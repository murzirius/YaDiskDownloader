# Восстановление нечитаемых сведений истории

Сборка 1.4.3, номер 20261021.6.

## Причина и исправление

При чтении некорректного текста Python SQLite вызывает `OperationalError` без `sqlite_errorcode`. Прежняя обработка показывала общий `SQLITE_ERROR`, а подготовка дозагрузки останавливалась при переносе сведений для сравнения загрузок.

Текст этих сведений теперь читается как последовательность байтов с учётом кодировки SQLite. Нечитаемая запись помечается как непроверенная. Текущий список заново поступает с Яндекс.Диска; проверка размеров, содержимого и готовых копий не ослабляется. Для непроверенной старой записи нельзя достоверно сообщать об изменении или удалении источника.

Старое задание в базе приложения не изменяется. Перед обновлением переносимой описи с нечитаемыми сведениями создаётся отдельная резервная копия через SQLite Backup API. Она записывается во временный файл, синхронизируется и публикуется без перезаписи чужих файлов. Её имя не совпадает с шаблоном поиска рабочей описи. Отмена сохраняет исходную опись и удаляет только собственный временный файл.

Для старых CMD-сред безопасный снимок SQLite с журналом DELETE теперь сохраняет и двоичные значения. Буфер временного файла настроен на 1 МиБ; большие снимки сбрасываются на диск; текстовые строки не превращаются в двоичные значения при восстановлении снимка.

## Проверки

- Регрессионный сценарий сначала воспроизведён на исходном коде и опубликованном EXE 20261021.5: остановка до обхода источника, `OperationalError` без кода SQLite, цепочка `_run → inherit → copy → records`.
- Исправленный настоящий EXE проверен с историей приложения и переносимой описью по 1000 тестовых файлов: подготовка проходит, исходная история сохраняется, содержимое всех файлов совпадает по SHA-256.
- Проверены получение свежих сведений через тестовый API, отсутствие повторного скачивания готового оригинала, отметка сравнения «Не удалось проверить», сохранность исходных данных, отмена резервного копирования и выбор рабочей описи при более новой резервной копии.
- Проверены UTF-8, UTF-16le, UTF-16be и двоичные значения при сбросе ограниченного снимка на диск.
- Полный локальный прогон после основной правки: 518 тестов пройдено, 1 пропущен из-за прав Windows на ссылки, 238,25 с. Дополнительный прогон проверок восстановления: 10 тестов пройдено.

## Производительность и ограничения

На одинаковой искусственной истории из 55 000 файлов и 20 000 записей результатов подготовка заняла 10,3662 с до изменения и 10,3015 с после. CPU: 6,6875 и 6,7344 с соответственно. По одному прогону нельзя заявлять ускорение; заметного ухудшения в этом сценарии не выявлено. Проверок путей файловой системы при переносе метаданных — 0 в обоих случаях.

Это проверка метаданных на локальном диске; пиковая RAM и физический дисковый ввод-вывод не измерялись. Реальный аккаунт Яндекс.Диска и физический NAS не использовались. Восстановление ограничено нечитаемыми сведениями для сравнения загрузок: недопустимые имена, пути и другие неизвестные повреждения не принимаются молча.
